## Entry conditions

- `v0.6.0` is tagged at `29e0ef6`. The tag's release notes carry the operational
  caveats: GitHub Actions had no runner, the release ceremony has only run with
  throwaway keys, and the native services have not been exercised on a
  deployment host. This plan and the close report are the only commits after the
  tag; the `v0.7.0` branch starts from them.
- D9–D20 are accepted in §16. A phase that needs a decision the log does not
  have stops and asks; it does not guess.
- The `v0.6.0` branch is closed for features. Fixes go to `v0.7.0` or a patch
  tag, not to the frozen line.

## Strategy

1. **Contract before mechanism.** Manifest v4 is the first phase because every
   later phase declares intent in it: roots, listeners, `{broker}`.
2. **Sandbox before privileged services.** A proxy on `:443` and a container
   manager holding a runtime socket are only supportable once the filesystem is
   narrowed and the port capability is granted deliberately. L1 and the port half
   of L3 are v0.7.0 scope, not a later hardening pass.
3. **Broker before the first consumer.** `certs` and `acme` are the first
   service-to-service call; the audit bridge rides the same socket.
4. **One app per phase**, demoable and removable on its own, with its removal
   row asserted by a golden test.
5. **A debug preview is not the release.** If L1 or the port capability slips,
   v0.7.0 is not tagged; the plan does not grow a "preview" escape hatch.
6. **No feature logic in the engine.** Anything that cannot be a bundle, a
   service or an SDK addition is a design problem, not an engine patch.

## Manifest v4

The contract change every phase leans on. `manifest_version = 4` is optional: a
v3 manifest keeps its exact meaning and is still accepted; a bundle that declares
roots, listeners or a broker becomes v4.

```toml
[service]
path = "bin/proxy"
sha256 = "…"
class = "socket"
argv = ["--socket", "{socket}", "--data", "{data}", "--shared", "{shared}",
        "--broker", "{broker}", "--http", ":8080", "--https", ":8443"]
listen = ["tcp:8080", "tcp:8443", "tcp:443"]
egress = ["any"]                       # or ["host:443", "10.0.0.0/8:5432"]
roots  = ["/etc/ssl:ro", "/var/run/docker.sock"]
```

- **`{broker}`** is a new argv placeholder beside `{socket}`, `{data}` and
  `{shared}`, at most once. The broker socket is the service's identity; the
  grant authorizes what it may call.
- **`roots`** lists the paths the service may touch. `{data}`, `{shared}`,
  `{socket}` and `{broker}` are implicit and a second declaration is an error. A
  `:ro` suffix is required for read-only roots. The engine state is not offered
  as a root; a broad root such as `/` is shown at approval, and the engine's
  `0700` state stays unreadable to the app's uid.
- **`listen`** is `tcp:<port>`, `tcp:<ip>:<port>` or `udp:<port>`; the engine
  refuses anything else and never allocates or reserves a port.
- **`egress`** is `any` or a list of `host:port` / `cidr:port`. In v0.7.0 it is
  **intent shown at approval, frozen in the grant, and not enforced**: network
  isolation is L2, scheduled after v0.7.0. The approval text says so.
- **Enforcement in v0.7.0:** roots by L1 (per-service uid plus Landlock), listeners
  below 1024 by the port capability. Nothing else is claimed.
- The approval surface shows roots, listeners and egress with their mode; the
  grant freezes them; changing any of them is a new approval, not an edit.

## Phases

### Phase 0a — Manifest v4 and the accepted decisions

**Objective:** a v4 manifest parses, validates, appears at approval and is frozen
in the grant; v3 bundles are unchanged.

**PR:** `feat/v4-service-intent` → `v0.7.0`
- Scope: parser and validation for `listen`, `egress`, `roots`, `{broker}`;
  `ServiceView` and the approval diff; grant fields; docs §7, §19, §22; D10 in
  §16; golden manifests untouched (still v3).
- Acceptance: a v4 bundle installs and `GET /api/engine/apps/{id}` shows the
  intent; a malformed listener, an unknown root mode, a second `{data}` or a
  second `{broker}` is refused with a typed error; a v3 bundle installs exactly
  as before.

**Features**
- `Manifest::service` gains the three fields, gated on `manifest_version = 4`.
- `ServiceLaunch` substitutes `{broker}`; the broker path is
  `state/broker/<app-id>.sock`.
- The grant stores the frozen intent and the approval view renders it.

**Unit tests:** accept/reject per field; placeholder counts; v3/v4 equivalence
for a service with no new fields; grant round-trip.
**E2E:** install a v4 fixture bundle and read the approval surface through the
API.
**Dependencies / risks:** none; this is the contract slice. Risk: growing the
manifest without a consumer, which is why the fields are inert until 0b/0c.

### Phase 0b — Sandbox L1 and the port capability

**Objective:** a service sees only its declared roots and can bind a declared
privileged port when the engine is allowed to grant it; everything else is a
typed `service.deny`.

**PR:** `feat/sandbox-roots` → `v0.7.0`
- Scope: per-service uid (or a per-service subordinate uid when the host has
  none), Landlock rules over the roots and the implicit directories, capability
  handling for `listen` ports below 1024, `service.deny` with the layer and
  reason, docs §28.
- Acceptance: the `fs` fixture cannot read `state/apps` or another service's
  `{data}`; a declared `/etc/ssl:ro` root is readable and not writable; a service
  that binds 443 succeeds only when the engine holds `CAP_NET_BIND_SERVICE`
  (root or ambient), and is refused with `service.deny` otherwise; the audit
  entry names the layer.

**Features**
- L1: `setresuid` to the app's uid, `PR_SET_NO_NEW_PRIVS` kept, Landlock rules
  from `roots` (read/write or read-only), `{socket}`/`{data}`/`{shared}`/`{broker}`
  implicit. The app's `{data}` and socket are prepared for its uid; `{shared}`
  stays the trust domain. The engine state is `0700` and owned by the engine, so
  a non-engine uid cannot read it even when a declared root covers `/`.
- L3 (ports only): the supervisor adds `CAP_NET_BIND_SERVICE` to the child's
  permitted/effective sets before exec when a declared listener is privileged,
  and drops every other capability from the bounding set. No `setuid` binary and
  no file capability is needed; `no_new_privs` stays on because the privilege is
  already held at exec.
- A host without Landlock or without the capability refuses the launch instead
  of silently running the service unconfined.

**Unit tests:** root parsing and implicit roots; a declared privileged listener
without the capability; `service.deny` fields; uid allocation and reuse.
**E2E:** a fixture service that reads outside its roots is denied; the real `fs`
service still reads `/` when approved; the proxy fixture binds 443 when the
test runs as root (skipped with a reason otherwise).
**Dependencies / risks:** 0a. Risk: hosts without Landlock (kernel < 5.13) — the
engine refuses or degrades the service; documented. Risk: allocations of uids on
hosts where the engine is not root — the release runs the engine as root or with
the capability; an unprivileged engine supports only high ports.

### Phase 0c — Broker, audit bridge and surface exports

**Objective:** a service calls another service's interface through its grant,
with budgets and audit, and the panel can discover a provider by interface.

**PR:** `feat/service-broker` → `v0.7.0`
- Scope: per-caller broker socket, call and stream protocol (the same
  `interface#function` + JSON shape the private service socket already uses),
  grant and budget checks, audit record, generated service client,
  `anth:audit/record@1.0.0` served by the broker, `SurfaceApp.exports`, docs §22.
- Acceptance: a fixture consumer calls its provider through `{broker}`; a call
  without a grant is denied and audited; a stream ends with `exhausted` at its
  budget; `GET /api/engine/composition` lists `exports` and the manager finds the
  provider by interface; removing the provider degrades the consumer without a
  fatal.

**Features**
- The broker resolves the interface to the composed provider, applies the same
  grant and budget checks as `AppCaller`, and audits every call with the caller,
  callee and result.
- The audit bridge is a broker-served native interface; the detail is sanitized
  by the engine's existing rules.
- `SurfaceApp.exports` is generic surface data; the manager checks the provider's
  descriptor tier before using it.

**Unit tests:** grant denial, cycle refusal, budget exhaustion, audit shape,
surface exports for a composed app.
**E2E:** two fixture services in one composition; a consumer call, a denied call,
a removed provider.
**Dependencies / risks:** 0b (denials must be enforceable per caller). Risk: the
broker becomes a second router; it must reuse `AppCaller` rules instead of
re-implementing them. The file-drop fallback of §22 §1 is **removed from the
plan**; if the broker slips, the phase slips.

### Phase 1 — Certificate manager

**Objective:** one inventory of certificates with expiry and chain state, and a
publish directory the proxy can read.

**PR:** `feat/certs` → `v0.7.0`
- Scope §23: C1 inventory (scan roots, status, expiry buckets) and C2 import,
  publish atomically to `{shared}/tls/<id>/`, remove, `auto-renew` flag, WIT,
  routes, CLI, panel view, audit.
- Acceptance: import a matching chain/key and publish it; a mismatched key is
  refused before anything is written; the private key is never returned by WIT,
  a route, a log or the panel; an expired certificate shows `expired`; removing
  the app keeps the published files and the panel shows the missing provider.

**Unit tests:** PEM parse/match, expiry boundaries, publish permissions (`0600`),
atomic replace, import with an unknown root, removal keeps files.
**E2E:** import → publish → the proxy fixture reads the published directory; the
removal row of §21 §5 with the golden composition.
**Dependencies / risks:** 0a, 0c. Risk: `/etc/letsencrypt` layouts vary; C1 reads
them but never copies keys out.

### Phase 2 — Reverse proxy

**Objective:** the edge: two hosts, TLS from the published directory, WebSocket
and HTTP/2, whole-document apply with rollback.

**PR:** `feat/proxy` → `v0.7.0`
- Scope §25: P1 HTTP vhosts and path routes, P2 TLS/SNI/reload from
  `{shared}/tls`, P3 WebSocket, HTTP/2, header policy and body limits; routes,
  CLI, panel, access-log stream, audit for apply.
- Acceptance: two hosts route to two upstreams; a bad apply rolls back to the
  last good document and keeps serving; TLS reloads without a restart; a
  WebSocket echo works; HTTP/2 negotiates; the access log is lossy only under
  budget and reports the dropped count.

**Unit tests:** route precedence, host/SNI parsing, apply versioning and
rollback, header policy, budget accounting.
**E2E:** a loopback panel with two fixture upstreams, TLS from a fixture
certificate, a WebSocket echo, an h2 request.
**Dependencies / risks:** 1, 0b (port 443 when declared). Risk: HTTP/2 server
support (h2 + rustls ALPN) is a real implementation slice; if it slips, P3 ships
WebSocket and HTTP/1.1 and the DoD is amended, not silently weakened.

### Phase 3 — ACME

**Objective:** issue and renew against an RFC 8555 CA, HTTP-01 through the proxy
and DNS-01 through a solver, with the certificate manager storing the result.

**PR:** `feat/acme` → `v0.7.0`
- Scope §24: A1 accounts/orders/staging, A2 HTTP-01 via `{shared}/acme/http-01`
  and `store-issued` on `certs`, A3 renewal from `auto-renew` plus ARI, A4 DNS-01
  with `manual`, `rfc2136` and `webhook`, A5 revocation with a reason code;
  routes, CLI, panel timeline, audit.
- Acceptance: against a local Pebble, an account is created, an order completes,
  the certificate lands in `certs` and the proxy serves it; renewal runs off the
  `auto-renew` flag; a staging order is never promoted; DNS-01 works with the
  manual solver in the fixture and a webhook in the QA matrix.

**Unit tests:** account key custody, order state machine, backoff and jitter,
staging/production separation, solver validation, no secret in a log or route.
**E2E:** Pebble in the test harness for A1–A2, a DNS solver fixture for A4;
Let's Encrypt staging stays a manual QA row.
**Dependencies / risks:** 2 (HTTP-01 needs the proxy), 0c (certs). Risk:
external CAs are not deterministic; Pebble is the gate and the real CA is the
release QA, not CI.

### Phase 4 — Containers

**Objective:** a Docker-compatible runtime behind the approval, with lifecycle,
logs, stats and exec, and no ambient host reach beyond the approved socket.

**PR:** `feat/containers` → `v0.7.0`
- Scope §26: inventory, create/start/stop/restart/remove, logs tail+follow,
  stats, exec over the terminal layer, images, named volumes; routes, CLI, panel,
  audit per mutation; no bind mounts, no privileged mode.
- Acceptance: list, start, stop, read logs and exec a container from the panel;
  a bind mount or privileged flag is refused; no environment value appears in a
  log or audit record; a missing runtime socket is a clear degraded state.

**Unit tests:** API fixture (JSON over a Unix socket) for lifecycle, refusal of
mounts/privileged, log budget, audit shape.
**E2E:** fixture runtime for CI; Docker and rootless Podman as manual QA rows.
**Dependencies / risks:** 0b (the runtime socket is a declared root), 0c (audit).
Risk: the socket is root-equivalent; the approval text and the docs say so.

### Phase 5 — Store and the manager handoff

**Objective:** browse a signed catalogue, download a digest-pinned bundle, and
install it through the manager with the operator's explicit approval.

**PR:** `feat/store` → `v0.7.0`
- Scope §27: index format and verification, `native` and `github` sources,
  cache and search, download stream with the 32 MiB cap, manager handoff that
  shows the engine-computed risk, the publisher fingerprint and the keyring
  action when the signer is not trusted; routes, CLI (read-only), panel; docs.
- Tooling: `anth-sign file <path> --key <key>` writes `<path>.sig` from the exact
  bytes, so a catalogue can be published without writing a signer. The store
  verifies with the same Ed25519 primitives (exposed through the service SDK).
- Acceptance: a signed fixture catalogue lists an app; a tampered index or a
  digest mismatch is refused and the previous cache is kept; installing an
  untrusted publisher requires an explicit `key add` in the handoff; the store
  never installs or approves on its own.

**Unit tests:** index parse and signature over exact bytes, tampered signature,
digest mismatch, cap and idle timeout, cache keys, untrusted publisher flow.
**E2E:** a fixture source over loopback (native) and a GitHub-shaped source; the
manager handoff through the API.
**Dependencies / risks:** 0a, 0c. Risk: two trust decisions (index key and bundle
signer) are easy to conflate; the UI and docs keep them separate.

**Objective:** the DoD of §21 §10, proven on the edge composition.

**PR:** `feat/v0.7-hardening` → `v0.7.0`
- Scope: the removal matrix as a golden test with the edge composition (signed by

  manual QA matrix is complete; a tag `v0.7.0` is cut from the branch.

## Cross-cutting rules

- **Contract changes are decisions.** A new manifest field, a new native
  interface or a new placeholder updates §16 in the same PR.
- **Audit everything that changes state**, including broker calls, certificate
  imports, proxy applies, container mutations and store downloads.
- **No secrets** in a route, a log, an audit record, a stream or the panel; the
  detail carries identifiers and fingerprints only.
- **Streams obey §20.** A hard budget ends with `exhausted`, never a silent
  truncation; the access log is the one lossy stream and reports the drop count.
- **Each phase** updates its docs and carries unit tests; e2e is fixture-based
  where a real host is not reproducible, with a manual QA row instead of a claim.
- **CI is the gate when it returns.** Until GitHub has a runner, every phase runs
  the same commands locally: the three Rust workspaces, fmt, clippy, the edge
  gate and the acid test.

## Definition of done

§21 §10, unchanged: import or issue a certificate and serve HTTPS; renew without
an operator; route two hosts with WebSocket and HTTP/2; operate a container
without SSH; install a signed bundle through the manager with explicit approval;
remove any of the five apps with the expected degradation; pass conformance, the
removal matrix and the manual QA matrix with no secret anywhere.

## Risks

- **Five apps is a large milestone.** The phases are independent; if one slips,
  the milestone stops at the last complete app instead of shipping a half app.
- **No L2 means no egress enforcement.** The manifest says so; an operator who
  needs enforced egress waits for v0.8.
- **No real-host validation here.** The release gate includes a manual QA matrix
  on a deployment host; the fixture tests are the automated half, not a
  substitute.
- **Root or capability for privileged ports.** A deployment that runs the engine
  unprivileged gets high ports only; the release notes say it.
- **Store trust is two keys.** Index signing and bundle signing are independent;
  conflating them is the failure mode the UI and docs must prevent.
