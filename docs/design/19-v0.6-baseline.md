# 19. v0.6.0 baseline and service contract

> Part of the [design index](../../DESIGN.md). Phase 0 of
> [§18](18-v0.6-plan.md).

Status: **accepted**. This document fixes the v0.5.0 baseline, reduces the v0.4
feature set to a reference checklist, and settles the service, host-emulator,
filesystem and terminal contracts before engine code.

## 1. Baseline

The code and contract baseline is the `v0.5.0` tag (`ea3b86d`). v0.6.0 adds
services and system apps on top of that contract; it does not re-implement v0.4.

The v0.4.0 tag (`v0.4.0-freeze`) is a **scope reference only**. Its code, native
ABI, flat type language and v2/v3 dual manifest paths are not copied. A v0.4
behaviour is in scope only when it is listed in §2 and mapped to a v0.6 app.

## 3. Manifest v3: one WIT API, three shapes

A v3 app may carry `[service]`, `[wasm]`, or **both**. At least one is required.
v2 apps keep working unchanged.

- **Service-only:** `[service]` with binary path, sha256, class, argv and socket;
  WIT exports; no `[wasm]`.
- **Wasm-only:** the v2 shape under v3.
- **Hybrid:** `[service]` and `[wasm]` in the same bundle. The service and the
  component export **disjoint** interfaces; a duplicate export is a manifest
  error.

The public API is always WIT. There are no raw service routes.

```toml
manifest_version = 3

[app]
id = "org.anthracite.fs"
namespace = "anthracite:fs"
name = "Files"
version = "0.1.0"

[service]
path = "bin/fs"
sha256 = "…"
class = "host"
argv = ["--socket", "{socket}", "--root", "/"]

[[export]]
interface = "anthracite:fs/read@1.0.0"

[[route]]
method = "GET"
path = "/files"
call = "anthracite:fs/read@1.0.0#list"

[[cli]]
call = "anthracite:fs/read@1.0.0#list"
verb = "files"

[[slot]]
id = "panel.view"
label = "Files"
tag = "files"
module = "web/files.js"
sha256 = "…"
```

Rules:

- v3 requires at least one of `[service]` or `[wasm]`.
- A service requires `wit/` and at least one `[[export]]`; a service with no
  public interface is invalid.
- `[wasm]`, `[[export]]`, `[[import]]`, `[[route]]` and `[[cli]]` keep their v2
  meaning. A service export is a provider in the same interface graph as a wasm
  export.
- `[[route]]` and `[[cli]]` keep calling `interface#function`; the engine resolves
  the provider (wasm or service). The panel, CLI and generated clients do not
  know the difference.
- `[[slot]]` is allowed with either half, or both.
- `path` is exactly `bin/<file>`; no subdirectories, no traversal. The binary is
  hashed with `sha256` and verified. The bundle may carry `bin/`, `wasm/`, `web/`
  and `wit/` together.
- `argv` has 1–64 entries, each at most 4 KiB, no NUL, and exactly one
  `{socket}` placeholder. No other placeholders are expanded.
- `class` is one of `exec`, `socket`, `device`, `admin`, `host`, mapped to the
  existing risk ladder:
  - `socket`, `device`, `admin` → `admin`;
  - `exec`, `host` → `host`.
  A service always requires at least `admin`. The service class risk is included
  in the app's risk and propagates to consumers that import its interfaces.
- `class` and `argv` are frozen in the grant and shown in approval. A service
  binary swap is a new approval.
- The native set stays closed: a service exports only app namespaces, never
  `anth:*`.

## 4. Service lifecycle and WIT-RPC

The service is a **provider transport**, not a second API.

- The supervisor creates `state/run/` (`0700`) and a socket per running service,
  `state/run/<app-id>.sock` (`0600`). It is removed on stop and on boot.
- Launch: `bin/<path>` with the allowlisted argv, `{socket}` replaced by the
  handoff path. No state path, data directory or root is passed unless the
  manifest's argv declares it (the `fs` case).
- Readiness: the service must answer `GET /health` over the socket within
  `limits.start-timeout-ms` (default 5s). A slow service is degraded, not a hang.
- Stop: `SIGTERM`, 5s grace, `SIGKILL`; remove the socket; kill the process group.
- Crash: restart with bounded backoff (3 attempts in 60s); then degraded; audit
  `service.start`, `service.stop`, `service.crash`, `service.deny`.

The private call protocol:

```http
POST /__anth/call
{"interface":"anthracite:fs/read@1.0.0","function":"list","input":{…}}

200 {"ok": …}
4xx/5xx {"error": {…}}   # the contract envelope
```

- `ServiceCaller` implements the same `AppCaller` used by wasmtime.
- A composed `AppCaller` resolves each app to a wasm caller or a service caller.
- The engine validates the input and output against the WIT types with the same
  JSON mapping used by HTTP routes and the generated clients.
- The service never sees `/api/apps/...` paths; it sees interface, function and
  input only.
- Answers carry `Content-Length`; the supervisor reads until the connection
  closes, so a keep-alive answer is a hung call until the deadline.
- Payloads are capped (4 MiB per call initially); larger transfers are M5 streams.
- The service SDK deserializes the input into the WIT types it generated, so a
  bad payload is refused before the handler runs. Engine-side validation against
  the same types is the follow-up once the shim and the shared codec land; the
  transport must not become a second interpretation of the types.
- Phase 1 launches the child as the engine user. The class is **risk**, not a
  sandbox yet: privilege drop, namespaces and per-class OS limits belong to the
  hardening pass, and they are why third-party services stay behind the startup
  switch.

## 5. Host emulator

`demo/emulator` (the plan's `apps/host-emulator`; the “name may change” clause is
settled) is a **native service** with deterministic fixtures, class `socket`,
unprivileged and outside the wasm `apps/` workspace. One binary serves **one
bundle per app**, because a bundle carries exactly one WIT package and one world:
`anthracite:fs`, `anthracite:terminal`, `anthracite:proc`, `anthracite:net`,
`anthracite:storage` and `anthracite:accounts`. Each bundle keeps the future real
app's package, so replacing the provider does not touch the UI and removing one
app does not remove the rest.
Every bundle implements the same `/__anth/call` protocol and exports:

- `fs`: a fixture tree with files, directories and trash; write/edit is in-memory
  and resets on restart.
- `terminal`: a scripted session with a prompt, `help`, resize and close.
- `proc`: stable synthetic pids/start_ticks, CPU/memory and allowlisted signals;
  a signal updates the fixture state.
- `net`: interfaces, addresses, counters and routes; read-only in this slice.
- `storage`: devices, mounts and usage; read-only in this slice.
- `accounts`: users and groups with system/locked flags; read-only in this slice.

The emulator is not engine code. It is removable and exists only to build the UI
and the service protocol quickly. Real services replace it by changing the
provider in the composition. It never gets the host root.

Real system apps may be service-only or hybrid; the emulator is service-only so
it can be swapped without changing the UI bundle.

The six packages are fixed in `demo/emulator/bundles/` (not illustrative):
`anthracite:fs@1.1.0` exports `read` (`list`, `stat`, `read-file`, `trash`) and
`write` (`write-file`, `mkdir`, `remove`, `rename`, `restore`);
`anthracite:terminal` exports `terminal`
(`open`, `list`, `read`, `write`, `resize`, `signal`, `close`);
`anthracite:proc@1.1.0` exports `proc` (`list`, `signal`, `spawn`); `anthracite:net@1.1.0` exports `net` (`interfaces`, `routes`, `set-up`,
`add-route`, `remove-route`); `anthracite:storage@1.1.0` exports `storage` (`devices`, `mounts`,
`attach`, `detach`); `anthracite:accounts` exports `accounts` (`users`,
`groups`). The real apps implement the same ids, so an upgrade replaces the
provider in place.

## 6. `fs` host root

The real `fs` service is class `host` and declares its root in the signed argv
(`--root /` by default). The operator sees the root, class and argv at approval
and the grant freezes them. The service enforces the root for every operation;
the wasm UI never receives a host path, only a WIT call. Traversal, symlink escape
and non-UTF-8 names are typed refusals. `storage` owns mounts; `fs` does not mount
anything.

## 7. Terminal interface

The terminal exports WIT functions, not HTTP endpoints. Shapes are illustrative;
Phase 5 fixes the exact WIT:

```wit
interface terminal {
  record session { id: string, shell: string, owner: string, seq: u64 }
  record output { seq: u64, data: list<u8> }

  open: func(shell: string, cols: u32, rows: u32) -> session;
  list: func() -> list<session>;
  read: func(id: string, seq: u64, wait_ms: u32) -> option<output>;
  write: func(id: string, data: list<u8>);
  resize: func(id: string, cols: u32, rows: u32);
  signal: func(id: string, signal: string);
  close: func(id: string);
}
```

- Owner, seq and idle limits live in the service.
- `session.seq` is the last sequence the service emitted; a reader starts at `0`
  and advances by one per chunk. The fixture returns immediately; the real
  service uses `wait-ms` for the bounded long-poll.
- `read` is the bounded long-poll; Phase 8 replaces polling with `stream<u8>`
  without changing the app-facing route.
- Routes and CLI are generated from this WIT exactly like a wasm app.

## 8. Open mapping

- v0.4 host cards: `proc` exposes the metrics; `manager` may own the overview
  view. Decide in Phase 7.
- Firewall stays inside `net`; if it grows its own policy surface, it becomes a
  separate app, not an engine feature.
- Policy switches (`fs` root, `net` apply, `storage` mount/format) are operator
  configuration shown at approval; the exact config file is settled in Phase 4.
- Service host imports (`anth:env`, `anth:store`) are not in Phase 1. A service
  uses the OS under its class; the RPC host-import bridge is a later phase.
- App-to-app imports from a service need the generated component shim (§10).

## 9. Third-party system apps

A service is no longer reserved to the system tier, but it is never silently
allowed. The daemon config has a startup-only switch:

```toml
[services]
allow-third-party = false
```

- Default **false** in a release build. A third-party bundle that declares
  `[service]` is refused at install with `denied`.
- The **debug profile** turns it on (`Config::debug`), because the host emulator
  is a third-party bundle and a developer build has no system key yet. The
  release template keeps `false`; the switch is still logged as a warning when
  it is on.
- When **true**, a third-party signed bundle may install, approve and compose a
  service. The class, argv, root and binary hash are shown at approval; the
  operator still accepts the risk.
- The switch is read once at boot, logged as a warning, and reflected in the
  composition view. Turning it off and restarting stops third-party services and
  degrades their consumers; it does not delete their state.
- System-tier apps are unaffected by the switch.
- This is an explicit deployment decision, not a manifest field: an app cannot
  grant itself the service kind.

## 10. Adapter and shim

- `ServiceCaller` is the engine-side adapter; it implements the existing
  `AppCaller` and maps RPC errors to the contract error kinds.
- `sdk/rust/service` is the service-side adapter: the socket server, `/health`,
  the `/__anth/call` dispatcher, the JSON codec and the contract error envelope.
  Its v0 `Handler` dispatches by `interface` and `function` strings; a typed
  trait generated from WIT is the next step, and the emulator is built on the v0.
- `sdk/ts/service` is optional later.
- The HTTP↔WIT value mapping is extracted so routes, CLI and RPC share one codec.
- A service that is a **provider to another wasm app** needs a generated shim
  component: it exports the provider interface and imports an engine host call
  that forwards to `ServiceCaller`. Until the shim lands, a service can serve its
  own routes/CLI but is not importable by other apps.
- The shim is scheduled when the first real consumer imports a service interface
  (likely `manager` importing `fs`), not in Phase 1.
