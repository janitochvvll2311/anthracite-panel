# 19. v0.6.0 baseline and service contract

> Part of the [design index](../../DESIGN.md). Phase 0 of
> [§18](18-v0.6-plan.md).

Status: **accepted**. This document fixes the v0.5.0 baseline, reduces the v0.4
feature set to a reference checklist, and settles the service, host-emulator,
filesystem and terminal contracts before engine code.

## 1. Baseline

The code and contract baseline is the `v0.5.0` tag (`ea3b86d`). v0.6.0 adds
services and system apps on top of that contract; it does not re-implement v0.4.

The v0.4.0 tag (`v0.4.0-freeze`) is a **scope reference only**. Its code, native
ABI, flat type language and v2/v3 dual manifest paths are not copied. A v0.4
behaviour is in scope only when it is listed in §2 and mapped to a v0.6 app.

## 3. Service manifest v3

A service bundle is a new contract. v2 apps keep working unchanged. v3 adds:

```toml
manifest_version = 3

[app]
id = "org.anthracite.fs"
namespace = "anthracite:fs"
name = "Files"
version = "0.1.0"

[service]
path = "bin/fs"
sha256 = "…64 lowercase hex…"
class = "host"
argv = ["--socket", "{socket}", "--root", "/"]

[limits]
wall-ms = 5000

[[slot]]
id = "panel.view"
label = "Files"
tag = "files"
module = "web/files.js"
sha256 = "…"
```

Rules:

- v3 requires `[service]` and forbids `[wasm]`, `[[export]]`, `[[import]]` and
  `[[cli]]`. `[[slot]]` is allowed so the service can ship its UI.
- There is no per-route table: `/api/apps/{id}/*` (except the engine-reserved
  `/assets/*`) is proxied to the service. The service owns its HTTP surface.
- `path` is exactly `bin/<file>`; no subdirectories, no traversal. The binary is
  hashed with `sha256` and verified like the wasm component.
- `argv` has 1–64 entries, each at most 4 KiB, no NUL, and exactly one
  `{socket}` placeholder. No other placeholders are expanded.
- `class` is one of `exec`, `socket`, `device`, `admin`, `host`, mapped to the
  existing risk ladder:
  - `socket`, `device`, `admin` → `admin`;
  - `exec`, `host` → `host`.
  A service always requires at least `admin`, so no service is silently approved.
- `class` and `argv` are frozen in the grant and shown in approval. A service
  binary swap is a new approval.
- The tier rule is unchanged: a third-party bundle cannot be a service.

## 4. Service lifecycle and proxy

- The supervisor creates `state/run/` (`0700`) and a socket per running service,
  `state/run/<app-id>.sock` (`0600`). It is removed on stop and on boot.
- Launch: `bin/<path>` with the allowlisted argv, `{socket}` replaced by the
  handoff path. No state path, data directory or root is passed unless the
  manifest's argv declares it (the `fs` case).
- Readiness: the service must answer `GET /health` over the socket within
  `limits.start-timeout-ms` (default 5s). A slow service is degraded, not a hang.
- Stop: `SIGTERM`, 5s grace, `SIGKILL`; remove the socket; kill the process group.
- Crash: restart with bounded backoff (3 attempts in 60s); then degraded; audit
  `service.start`, `service.stop`, `service.crash`, `service.deny`.
- Proxy: HTTP/1.1 over the socket, `Connection: close` initially; method, path,
  bounded body and end-to-end headers. The engine adds `X-Anth-Actor` and
  `X-Anth-App`, strips hop-by-hop headers and inbound copies, and reserves
  `/assets/*` for its own asset route.
- Response: status and headers pass through; the engine caps the body and maps
  transport failures to `unavailable` with the service id.

## 5. Host emulator

`apps/host-emulator` (name may change) is a **service bundle**, class `socket`,
unprivileged, with deterministic fixtures. It implements the same HTTP protocol
as the real services:

- `fs`: a fixture tree with files, directories and trash; write/edit is in-memory
  and resets on restart.
- `terminal`: a scripted PTY with a prompt, `echo`, `help`, resize and exit.
- `proc`: stable synthetic pids/start_ticks, CPU/memory, signals return success
  for fixtures.
- `net`: interfaces, addresses, counters, routes; mutations update fixtures.
- `storage`: devices, mounts, usage; mount/unmount updates fixtures.
- `accounts`: users/groups; password changes update fixtures.

The emulator is not engine code. It is removable and exists only to build the UI
and the service protocol quickly. Real services replace it by changing the
provider in the composition. It never gets the host root.

## 6. `fs` host root

The real `fs` service is class `host` and declares its root in the signed argv
(`--root /` by default). The operator sees the root, class and argv at approval
and the grant freezes them. The service enforces the root for every operation;
the wasm UI never receives a host path, only the app proxy. Traversal, symlink
escape and non-UTF-8 names are typed refusals. `storage` owns mounts; `fs` does not
mount anything.

## 7. Terminal protocol (streams deferred)

The terminal is a service with a versioned HTTP contract; WIT streams land in
Phase 8.

| Method | Path | Purpose |
| --- | --- | --- |
| `POST` | `/sessions` | open a PTY (`shell`, `cols`, `rows`) → `{id, seq}` |
| `GET` | `/sessions` | list sessions with owner and idle time |
| `POST` | `/sessions/{id}/input` | write bytes (base64) |
| `GET` | `/sessions/{id}/read?seq=N&wait_ms=30000` | long-poll from `seq`, returns `{seq, data}` or `204` |
| `POST` | `/sessions/{id}/resize` | `{cols, rows}` |
| `POST` | `/sessions/{id}/signal` | allowlisted signal |
| `DELETE` | `/sessions/{id}` | close and kill the process group |

The service enforces owner, seq and idle limits. The UI polls `read`; Phase 8
replaces polling with `stream<u8>` without changing the app-facing route.

## 8. Open mapping

- v0.4 host cards: `proc` exposes the metrics; `manager` may own the overview
  view. Decide in Phase 7.
- Firewall stays inside `net`; if it grows its own policy surface, it becomes a
  separate app, not an engine feature.
- Policy switches (`fs` root, `net` apply, `storage` mount/format) are operator
  configuration shown at approval; the exact config file is settled in Phase 4.
