# 18. The v0.6.0 plan

> Part of the [design index](../../DESIGN.md).

Status: **accepted**. Base branch `v0.6.0`, cut from the `v0.5.0` tag at
`ea3b86d`. This document turns M4–M5 ([§11](11-roadmap.md)) into PR-sized phases;
the milestones remain those of the roadmap.

## Entry conditions

- `v0.5.0` is the code and contract baseline (M0–M3, auth boundary, quality pass).
- The v0.4 feature inventory is a **scope reference**, not the gate: v0.6.0 builds
  on the v0.5.0 contract.
- The release follow-ups in [§17 §0](17-deferred.md#0-v050-release-follow-ups) are
  operational: green CI once billing is restored, a GitHub Release, and an
  artifact workflow decision.

## Strategy

1. **Service apps first.** Terminal, fs, proc, net, storage and accounts need
   kernel-facing work; without the service contract they would leak ambient
   authority or force engine edits.
2. **Host emulator second.** A removable mock service implements the same
   protocol with deterministic fixtures, so the apps and panels can be built
   before the real services exist.
3. **Then one real service at a time**, tested on a real machine before the next.
4. **M4 first, M5 second.** The terminal is the real consumer that streams will be
   designed against.
5. **One phase per PR against `v0.6.0`.** Each phase is demoable and reversible.
6. **No feature logic in the engine.** A phase that cannot be expressed as a
   bundle, a service or an SDK addition is a design problem, not an engine patch.
7. **The panel stays a client.** New UI arrives as `panel.view`/`panel.settings`
   contributions.

## Service manifest (decision)

Service bundles use **`manifest_version = 3`**. Existing v2 apps keep working
unchanged. A v3 service:

- has `[service]` instead of `[wasm]`: binary path, sha256, class, argv allowlist
  and socket;
- has no WIT exports and no `[wasm]`; its routes are raw HTTP through the
  supervisor socket;
- may still carry `[[slot]]` UI modules and `[[route]]` entries for the engine to
  proxy;
- is refused on the v0.5.0 engine with an “unsupported manifest_version” error.

The binary hash lives in the signed manifest and is verified like the wasm hash.
The bundle layout gains a `bin/` (or `service/`) directory.

## Phases

### Phase 0 — Baseline inventory and ADRs

**PR:** `docs: v0.6.0 baseline inventory and service ADRs`

- Fix the v0.5.0 baseline and the v0.4 checklist as reference.
- Record the v3 service schema, classes (`exec`, `socket`, `device`, `admin`,
  `host`), argv allowlisting, socket handoff and the tier rule.
- Record the `fs` host-root model and the terminal HTTP protocol.
- Record that streams, events and quotas stay in M5.

**Done when:** decisions are in the decision log and the baseline checklist is
linked from [§13](13-migration.md). No engine code.

### Phase 1 — Service app contract

**PR:** `feat: service apps and the supervisor socket`

- Contract v3, registry/bundle support, grant/risk for service classes.
- Supervisor: launch, readiness, stop, crash isolation and audit.
- Router: proxy `/api/apps/{id}/*` to the service socket without handing the
  state tree to the app.
- A third-party service is refused at approval and compose.
- Fixture `echo-service` for the e2e.

**Done when:** the fixture installs, composes, answers over HTTP, is removed, and
its socket disappears.

### Phase 2 — Host emulator and demo composition

**PR:** `feat: deterministic host emulator`

- A removable service bundle under `apps/host-emulator` (name TBD in Phase 0)
  implementing the real service protocol with deterministic fixtures for
  fs/terminal/proc/net/storage/accounts.
- Unprivileged (`exec`/`socket`), no host root, no engine knowledge.
- `config.demo.toml` + `compositions/demo.toml` compose the emulator with the
  system UI apps.
- The real services later replace the emulator by changing the provider.

**Done when:** the same panel views render deterministic data from the emulator;
stopping it degrades the demo only.

### Phase 3 — System app UIs against the emulator

**PRs:** one per app, or paired only when they share no service code.

- `fs` explorer, terminal view, process list, network status, storage and
  accounts screens.
- All UI is a `panel.view` contribution; no engine feature names.

### Phase 4 — Real `fs`

**PR:** `feat: filesystem service`

- `host` class, operator-approved root (default `/`), explicit audit.
- The wasm UI never receives a path; it calls the service socket.
- Traversal, symlink escape and non-UTF-8 names are typed refusals.

**Done when:** the user tests it on a real machine and the emulator can be
removed from that composition.

### Phase 5 — Real terminal

**PR:** `feat: terminal service`

- PTY open/write/resize/signals/close/half-close over the versioned HTTP service
  protocol.
- Budgets for bytes and lifetime; a crash degrades only the terminal.

**Done when:** the user tests it on a real machine; no path or capability leaks
into the wasm UI.

### Phase 6 — Real proc, net, storage and accounts

**PRs:** one per app.

- `proc`: list and signal with allowlist and `admin`.
- `net`: status/read first; applying configuration is a separate approved flow.
- `storage`: disks, mounts and usage; read-only first.
- `accounts`: users/groups with `admin`.

**Done when:** each is removable and removing `net` leaves a working system, not
a broken panel.

### Phase 7 — Manager and M4 close

**PRs:** `feat: manager app`, `test: v0.6.0 system composition`

- Manager: installed apps, composition edits, approvals, enable/disable/remove.
- Golden composition of the system apps on the v0.5.0 contract.
- Remove `net` and assert the rest still boots and renders.

### Phase 8 — Streams, typed events and quotas (M5)

**PRs:** `feat: streams`, `feat: typed events`, `feat: stream quotas`

- `stream<T>`/`future<T>` and HTTP chunked/SSE mapping.
- Backpressure, cancellation, half-close and error-after-partial-data each with a
  conformance test.
- Events as `subscribe() -> stream<event>`; per-stream bytes/s and total quotas.
- Retrofit the terminal to WIT streams; the service HTTP protocol stays as the
  service boundary.

### Phase 9 — Conformance, third party and hardening (M5)

**PRs:** `feat: publish anth-conformance`, `feat: provider WIT fetch`,
`feat: audit and approval UI`, `feat: service sandbox`

- The kit runs offline against a bundle; `anth app fetch-wit` resolves provider
  packages.
- Panel settings: audit, risk and authority diff.
- Service sandbox hardening; Pulley decision after the sandbox.
- External bundle acid test: installs, composes, renders and answers.

## Cross-cutting rules

- **Manifest changes are contract changes.** v2 stays frozen; v3 is the service
  contract.
- **Service authority is narrower than the grant.** The grant lists interfaces and
  classes; the supervisor checks binary, argv and class.
- **No paths to wasm apps.** The `fs` service gets the host root; the UI gets only
  the service socket.
- **Audit every service lifecycle.** Launch, refusal, crash, stop and proxy denial.
- **CI:** every phase adds unit/e2e coverage; the v0.5.0 remote-client and edge
  checks stay.

## Open decisions

All Phase 0 decisions were agreed before engine work:

| # | Decision |
| --- | --- |
| P1 | Service bundles are `manifest_version = 3`; v2 apps are unchanged. |
| P2 | Streams/events/quotas wait for M5; the terminal uses a versioned chunked HTTP service protocol. |
| P3 | The real `fs` service gets an operator-approved host root; the wasm UI never receives paths. |
| P4 | `net` is read-only first; apply is a separate approval flow. |
| P5 | The v0.5.0 tag is the baseline; the v0.4 inventory is a scope checklist, not the gate. |
| P6 | Pulley waits until after the service sandbox. |
| P7 | The host emulator is a removable service bundle, not engine code. |

## Definition of done

- The system apps work on the v0.5.0 contract, and removing `net` leaves a
  working system.
- An app outside this repository installs, composes, renders and answers.
- The conformance kit fails loudly on a bundle that lies.
