# 18. The v0.6.0 plan

> Part of the [design index](../../DESIGN.md).

Status: **proposed**. Base branch `v0.6.0`, cut from the `v0.5.0` tag at
`ea3b86d`. This document turns M4–M5 ([§11](11-roadmap.md)) into PR-sized phases;
the milestones and the definition of done remain those of the roadmap.

## Entry conditions

- `v0.5.0` is tagged as the code baseline (M0–M3, auth boundary and quality pass).
- The release follow-ups in [§17 §0](17-deferred.md#0-v050-release-follow-ups) are
  operational, not blockers for code: green CI once billing is restored, a GitHub
  Release, and an artifact workflow decision.
- The service-app design choices below are settled in Phase 0 before engine code.

## Strategy

1. **M4 first, M5 second.** The system apps prove the contract and produce the
   terminal that streams are designed against.
2. **Service apps before feature apps.** Terminal, proc, net, storage and accounts
   need kernel-facing work; without the service contract they would either leak
   ambient authority or force engine edits.
3. **One phase per PR against `v0.6.0`.** Each phase is demoable and reversible.
4. **No feature logic in the engine.** A phase that cannot be expressed as a
   bundle, a service or an SDK addition is a design problem, not an engine patch.
5. **The panel stays a client.** New UI arrives as `panel.view`/`panel.settings`
   contributions, not as engine knowledge.

## Phases

### Phase 0 — Baseline inventory and ADRs

**PR:** `docs: v0.6.0 baseline inventory and service ADRs`

- Inventory the v0.4.0 feature baseline into a checklist: screens, operations,
  routes, persistence.
- Decide the service manifest shape (`manifest_version` bump or additive
  `[service]`), the classes (`exec`, `socket`, `device`, `admin`, `host`), argv
  allowlisting, socket handoff and the tier rule.
- Decide the `fs` confinement model and the terminal transport.
- Decide whether `net` starts read-only or also applies configuration.

**Done when:** the decisions are recorded in the decision log and the baseline
checklist is linked from [§13](13-migration.md). No engine code.

### Phase 1 — Service app contract

**PR:** `feat: service apps and the supervisor socket`

- Manifest and grant support for a service kind, with the declared binary, argv
  allowlist, class and socket.
- Supervisor: launch, readiness, stop, crash isolation and audit.
- Router: proxy `/api/apps/{id}/*` to the service socket without handing a path to
  an app; the service gets the socket, never the state tree.
- A third-party service is refused; the tier rule is enforced at approval and at
  compose.
- Fixture `echo-service` for the e2e.

**Tests/e2e:** argv violation, missing socket, crash/restart, third-party refusal,
UDS proxy, audit entries.

**Done when:** the fixture installs, composes, answers over HTTP, is removed, and
its socket disappears.

### Phase 2 — Terminal

**PR:** `feat: terminal service and view`

- PTY service: open, write, resize, signals, close, half-close.
- `panel.view` terminal UI, detached-window safe.
- Budgets for bytes and lifetime; a killed service does not take the engine down.

**Tests/e2e:** open a shell, run `echo`, read output, resize, close; a service
crash degrades only the terminal.

**Done when:** the terminal works in both panels, and removing it leaves no route
or slot behind.

### Phase 3 — Filesystem app

**PR:** `feat: filesystem app`

- Confined workspace: list, read, write, create, rename, remove.
- Traversal, symlink escape and non-UTF-8 names are refused with typed errors.
- `panel.view` browser; no engine knowledge of files.

**Tests/e2e:** read/write inside the root, traversal denied, symlink denied,
restart preserves content.

### Phase 4 — Process, network, storage, accounts

Split into one PR per app where the surface is non-trivial; `proc` + `storage`
may share a PR only if they share no service code.

- `proc`: list and signal with an allowlist and `admin` class.
- `net`: interfaces/status by default; applying configuration is a separate
  decision from Phase 0.
- `storage`: disks, mounts and usage; read-only first.
- `accounts`: users/groups; `admin` class.

**Done when:** each is a removable bundle and removing `net` leaves a working
system with that section gone, not a broken panel.

### Phase 5 — Manager and the demo instance

**PRs:** `feat: manager app`, `feat: deterministic demo composition`

- `manager`: installed apps, composition edits, approvals, enable/disable/remove.
- `config.demo.toml` with its own state and `compositions/demo.toml`; providers
  return deterministic data under the real interfaces.
- Demo isolation still shares state across browsers until per-user profiles land.

### Phase 6 — M4 acid test

**PR:** `test: v0.4 baseline composition`

- One composition that reproduces the baseline checklist.
- Remove `net` and assert the rest still boots and renders.
- A golden surface for the full composition.

### Phase 7 — Streams, typed events and quotas (M5)

**PRs:** `feat: streams`, `feat: typed events`, `feat: stream quotas`

- `stream<T>`/`future<T>` and the HTTP mapping (octet-stream/SSE).
- Backpressure, cancellation, half-close, error-after-partial-data: a conformance
  test per property.
- Events as `subscribe() -> stream<event>`; fan-out fixed at compose time.
- Per-stream bytes/s and total quotas from the grant budget.

### Phase 8 — Conformance, third party and hardening (M5)

**PRs:** `feat: publish anth-conformance`, `feat: provider WIT fetch`,
`feat: audit and approval UI`, `feat: service sandbox`

- The kit runs offline against a bundle; `anth app fetch-wit` resolves provider
  packages.
- Panel settings: audit, risk and authority diff.
- Service sandbox hardening; decide whether the Pulley profile ships.
- External bundle acid test: installs, composes, renders and answers.

## Cross-cutting rules

- **Manifest changes are contract changes.** Phase 0 chooses the versioning rule;
  old bundles either keep working or are refused with a typed error.
- **Service authority is narrower than the grant.** The grant lists interfaces;
  the service manifest lists a binary, argv and class, and the supervisor checks
  both.
- **No paths to apps.** Services receive sockets and handles, not filesystem
  paths from the engine.
- **Audit every service lifecycle.** Launch, refusal, crash, stop and proxy
  denial use the existing audit actor.
- **CI:** every phase adds its unit/e2e coverage; the v0.5.0 remote-client and
  edge checks stay in place.

## Open decisions

| # | Decision | Recommendation | Deadline |
| --- | --- | --- | --- |
| P1 | Service manifest: bump to v3 or additive `[service]` | Additive `[service]` under v2 if it can be refused cleanly; otherwise v3 with a migration test | Phase 0 |
| P2 | Terminal transport | Raw service HTTP now, WIT streams in M5; keep the service protocol small so the retrofit is bounded | Phase 0 |
| P3 | `fs` root | One explicit workspace root per app, no ambient home; mounts arrive with `storage` | Phase 0 |
| P4 | `net` scope | Status/read first; apply is a separate approval and audit path | Phase 4 |
| P5 | v0.4 baseline | The checklist from Phase 0, not "all of v0.4" | Phase 0 |
| P6 | Pulley profile | Decide after the service sandbox; never the default | Phase 8 |

## Definition of done

The v0.6.0 gate is the roadmap's:

- a composition of system apps reproduces the v0.4.0 feature baseline, and
  removing `net` leaves a working system;
- an app outside this repository installs, composes, renders and answers;
- the conformance kit fails loudly on a bundle that lies.
