# v0.2.0 — rewrite from the v0.1.0 lessons

Status: phases A–C are done. This document is the plan of record for the
v0.2.0 rewrite and the handoff for the phases that follow.

v0.1.0 shipped and is tagged. It works, and the suite is green: 919 Rust tests,
573 frontend tests. The rewrite is not a reaction to broken behaviour. It targets
four structural decisions that made every later phase more expensive than it
needed to be. Each one below is recorded with the evidence that produced it, so
the new tree can be judged against the same measurement.

## What v0.1.0 got right, and is therefore kept

These are not rewritten. They are ported, largely verbatim:

- **`/proc` parsing with the standard library only.** No `sysinfo`-style
  dependency, no `unsafe`, so the static musl build stays trivial. `collect_from`
  taking a filesystem root is why the parsers are testable at all.
- **The policy switches.** Every mutating feature is off in release and on only
  in the generated debug config, and an empty allowlist denies everything. That
  is the right default and the reason the panel is safe to expose.
- **Guards as one type per feature.** `ProcessPolicy`, `Guard`, `mount_root`
  containment and the partition guards are validated against a *fresh, unfitted*
  snapshot. Fitting a snapshot before a guard ran was a real bug in v0.1.0, and
  the rule that mutations read the unfitted view is worth keeping exactly.
- **The refusal to bootstrap over a config that will not parse.** Answering a
  parse error with defaults silently wiped an operator's settings.
- **`bun` only, musl only.** Both are fixed toolchain decisions, not preferences.
- **In-tree crypto.** PBKDF2 and HS256 over `hmac`/`sha2`/`base64`, and Ed25519
  through `ed25519-dalek`, keep the musl build free of C dependencies.

## Lesson 1 — the newline framing forced five truncation engines

`anth-proto` frames messages as newline-delimited JSON with a hard 1 MiB cap
(`MAX_LINE_LEN`). A snapshot that exceeded the cap could not be sent, so each
feature grew its own degrader that silently dropped data until the message fit:

| Module | `truncated`/`warning` mentions |
| --- | --- |
| `process/fit.rs` | 15 |
| `network/mod.rs` | 19 |
| `firewall.rs` | 18 |
| `volumes.rs` | 26 |
| `accounts.rs` | 46 |

Five implementations of the same idea, each with its own ordering rule (drop
diagnostics first, then rows by some priority), each with its own `total`/
`truncated`/`warning` fields, each needing its own test. Worse, 46 mentions in
`accounts.rs` is not a formatting concern: the account guards *needed* the
unfitted snapshot, so the module had to carry two collects to stay correct.

The cost is not the code volume. It is that **silent truncation is a correctness
hazard that has to be re-proven per feature**, and the policy "mutations read the
unfitted view" exists only because truncation exists.

**v0.2.0:** the wire is length-prefixed, not line-delimited, with a 64 MiB frame
limit. That is a transport limit on one message, not a data-loss rule. A list
that can legitimately exceed a comfortable frame paginates (`limit` + `cursor`)
and says so in the reply; nothing is dropped without the caller asking for it.
The five `fit_snapshot` passes and the `total`/`truncated`/`warning` triple
disappear, and `snapshot_json_len` — currently copy-pasted into five modules —
has no reason to exist.

## Lesson 2 — six per-feature error enums for one concept

`anth-proto` defines `ProcessSpawnErrorKind`, `FirewallErrorKind`,
`VolumeErrorKind`, `AccountErrorKind`, `FileErrorKind` and `NetworkErrorKind`.
They are near-identical: a variant per condition, mapped by hand to an HTTP
status in `api/error.rs`, and mapped again to an exit code in the CLI. Adding a
feature means adding a seventh enum and two more mappings, and the three
mappings can disagree — which is how a route answers `400` where the CLI exits
`1` for the same failure.

**v0.2.0:** one `ErrorKind` (`NotFound`, `Forbidden`, `Conflict`, `Invalid`,
`Unsupported`, `TooLarge`, `Internal`) carried by one `WireError`. The HTTP
status and the CLI exit code are derived from the kind in one place each. A
feature adds a *variant of a shared enum* only when the status genuinely differs.

## Lesson 3 — an operation touched four files, by hand

`Request` has 49 variants and `Response` 43, with 50 `Request::` arms in
`handler.rs`, 43 in `client.rs` and 9 in `daemon.rs`. The dispatch seam
(`Handler::blocks`, handler forwarding) was the right idea, but the *transport*
still required the same variant in two enums plus three matches. Nothing tied
them together, so a forgotten arm was a compile error at best and a silent
`None` at worst.

**v0.2.0:** one `Request`/`Response` pair per feature is generated from a single
declaration, and dispatch is a trait with a default "not mine" that the compiler
checks exhaustively per feature module. The CLI, the HTTP route and the daemon
share one `execute` entry point, so there is one place to add an operation.

## Lesson 4 — tests that encode an assumption instead of the contract

The v0.1.0 plugin phase shipped three defects the suite could not see
(`docs/design/platform-upgrades.md`, phase 8):

- the guest read an anchor body as an object while the host sends a JSON string,
  so the only mutating route answered `400` to every real request — the test
  hand-built the envelope and passed;
- `fixture!` returned early when the guest was unbuilt, so seven tests asserted
  nothing while `cargo test` reported success;
- the manifest declared a UI tag no module registered.

All three are the same shape: **a test that passes when its subject is absent.**

**v0.2.0:** a missing fixture panics with an actionable message, never returns
early. Every test drives the real entry point — the router, the socket, the
serializer — rather than a hand-built envelope. And there is CI, because v0.1.0
had none: `cargo fmt --check`, `clippy -D warnings` and the tests were a local
habit, which is how a suite can be green on a machine where the target was
installed and fail on a fresh clone.

## Target layout

```
backend/            Rust workspace root: the v0.2.0 daemon side
  anth-wire/        protocol: framing, one error type, messages  (no panel code)
  anth-host/        host inspection: pure /proc parsing
  anth-plugin/      the contract a guest links: envelopes, ABI, route table
  anth-panel/       daemon + client + HTTP, one vertical slice per phase
  .cargo/config.toml  the musl pin, owned by this workspace

frontend/           Bun workspace root: the v0.2.0 panel
  anth-wire/        what crosses the boundary: messages, errors, one exchange
  anth-webui/       the shell and its Vite build
  anth-plugin/      the contract a web module imports: endpoints, widget contract

plugins/            one directory per plugin, each a pair of independent projects
  hello/            manifest + backend/ (Rust cdylib) + frontend/ (Bun project)

v1/                 the frozen v0.1.0 tree: backend, frontend, plugins, docs
```

The tree is grouped by kind and each group is an independent project, which is
the layout v0.1.0 had. Two changes from that layout matter:

- **The plugin is a peer of `backend/` and `frontend/`, not a member of either.**
  A plugin is shipped to a third party, so it must build with nothing but its own
  directory. Keeping it out of the workspace root is what makes that testable:
  a stray `use` of a panel crate would fail the plugin build immediately.
- **`backend/` and `frontend/` are separate builds with separate lockfiles.**
  Neither installs the other's toolchain, so a Rust change does not need Bun and
  a frontend change does not need Cargo.

`v1/` keeps its own workspace, `.cargo/config.toml`, `Dockerfile`, docs and
CI-free status: it builds with `v1/` as the context and nothing at the root
imports from it. Phase F deletes it.

`anth-wire` stays separate for the same reason `anth-proto` was: an alternative
client must be implementable without the panel. The difference is that the
contract is now a length-prefixed JSON frame, which is what removes lesson 1.

## The plugin contract, as two libraries

The v0.1.0 plugin defect list above is a list of a plugin re-deriving the host's
contract by hand. Each entry is now the library's job:

| v0.1.0 defect | Where it is answered |
| --- | --- |
| the guest read a body as an object, the host sends a string | `anth-plugin::HttpRequest::body` is a `String`; `json_body()` parses it |
| the guest's arguments were `null`, the host needs a map | `Executor::exec_bare` passes `{}`; the crate's own test pins it |
| the manifest declared a tag no module registered | `@anth/plugin::registerWidget` is called once, idempotently |
| every widget reimplemented the anchor URL, the load states and the escaping | `@anth/plugin` exports one `PluginEndpoints` client and one `mountWidget` helper, and neither is inherited |
| the guest repeated ~130 lines of allocator and pointer work | `anth_plugin!` generates the four exports |
| the guest turned a CLI `argv` into an `HttpRequest` to reuse one handler | one type per pipe: a transport is read only in its own mapper |
| the guest named an HTTP status, so the CLI exit code was a second guess | `Status` is an enum; `code()` and `exit_code()` are exhaustive |
| the guest's reply of `null` served a `204` with the body `null` | `to_envelope` omits `body` when the value is null |

`backend/anth-plugin` is `no_std`, because a guest has no `std`; it is an
ordinary `rlib` the guest links, never a `cdylib`, so the plugin crate keeps
ownership of its one export file. `frontend/anth-plugin` is plain DOM rather
than Lit: a plugin is shipped to a third party, and binding it to the panel's Lit
version would break it on a panel upgrade.

That last rule is why the browser half is a contract and not a base class.
`PluginWidget` is an interface with a single method (`load`); presentation is the
plugin's own business, so one element can return markup, another can extend
`LitElement` and render from properties, and a third can paint a canvas. The
plumbing a widget usually wants is a separate, optional function: `mountWidget`
owns the shadow root, the load states and the retry button for the markup shapes,
and a plugin that already has a framework simply does not call it. The endpoint
client, `PluginEndpoints`, is likewise composed rather than inherited — it takes
the plugin id, origin, headers and `fetch` as configuration, so a module under
test and a module in production build it the same way.

A plugin may also declare an `alias` beside its `id`. The daemon resolves either
wherever an id is accepted — the socket, `plugin call`, `/api/plugins/{id}/…` —
and always answers with the canonical one. Directory order never decides: two
bundles claiming one alias is a conflict, exactly as two claiming one anchor is.

The pipes are the part worth stating as a rule. A single envelope with a `kind`
tag invites one `match` per transport, and the cheap way out of that `match` is
to fabricate the other transport's type — build an `HttpRequest` out of an
`argv` so one handler serves both. That lies about where the call came from, and
it silently caps one pipe at whatever shape the fabrication names: a plugin with
five anchors would answer one of them from `plugin call`.

So there are three entry points in the ABI, one per pipe, and no envelope:

```
anth_http(ptr, len)     {"method":..,"path":..,"query":{..},"body":..}
anth_cli(ptr, len)      "greet --name \"Ana Sol\""   (a JSON string)
anth_direct(ptr, len)   {"action":..,"value":..}
```

The host chooses the entry from the transport it is serving, so a guest cannot
read one as another. Each pipe then pays its own translation in the plugin:
`Plugin::from_http` and `Plugin::from_cli` return `Result<Request, Response>`, so
the mapper decides whether an unknown path is a `404` and a bad body a `400`.
`anth_direct` has no mapper because there is nothing to translate: `plugin call`
hands the plugin a `Request` in the plugin's own vocabulary, which is also what
makes a plugin testable without either transport.

`Request` names no transport — it is `{action, value}` — and the CLI's `value`
is whatever the mapper read from the command line (`command`, `args`, `flags`,
`options`).

The CLI payload is a **string**, not a list of words, for the same reason an HTTP
body is: the transport carries text and the plugin decides how to read it. A host
that sent `["greet", "--name", "Ana Sol"]` would be fine, but the same host
joining one back into a line for a log or a `plugin call` loses the boundary
between the flag and the value the moment a word contains a space — `--name Ana
Sol` is two words again. Keeping the line and resolving quotes (`'...'`, `"..."`
and backslash escapes) puts that decision where the knowledge is.
Two mappers therefore produce different `value`s for the same action, and that is
correct: each reports what its own transport carried. Requiring them to be
identical would force a mapper to invent a shape the caller never sent.

`Action(&'static str)` is a validated const rather than a `String` because a name
derived from a payload would let a caller invent an operation the plugin never
declared; `plugin call` resolves a name against `Plugin::actions()`, and anything
outside it is a `404`. `Status` is an enum for the same reason on the way out:
the plugin names an outcome, and the HTTP code and the CLI exit code are each
derived once, exhaustively, so a plugin cannot serve a `418` and two pipes cannot
disagree about a number neither owns.

Neither library is an authority. `anth-plugin` cannot decide which capability may
run — that is the manifest grant and `anth-panel`'s runtime — and `@anth/plugin`
refuses an absolute anchor URL so a module cannot reach a second origin with the
operator's session. A contract a guest links must not widen the guest's power;
`plugins/hello` is the proof it is enough for a real plugin, and it declares two
anchors and two CLI aliases over two actions so that "every pipe reaches the same
vocabulary" is a claim a test can check: `tests/manifest.rs` compares the
manifest's `[[api]]` paths against the HTTP mapper and each action against both
its anchor and its alias, both ways.

## CLI flags, the open question

The contract parses flags, but nothing types one yet. `CliArgs` resolves `-v`,
`--verbose`, `--name value`, `-n value` and `--` correctly, and the wasm guest
receives whatever `{"argv": [...]}` it is handed. The gap is upstream of both:
today `plugin call <id> REQUEST` takes one argument, a JSON payload, so a shell
user cannot write `--interface wg0` — they would have to hand-write
`{"kind":"cli","argv":["peers","--interface","wg0"]}`. v0.1.0 was the same, and
`anth-panel`'s dispatcher is `&[&CoreHandler]`, so no plugin is in the socket
chain at all.

Two places could parse the flags, and they are not equivalent:

| Who parses | The CLI works from a terminal | Cost |
| --- | --- | --- |
| the plugin, from `argv` | no | none today; already implemented and tested |
| the host, from manifest `[[cli]]` declarations | yes | the manifest becomes a second definition of the CLI |

Declaring subcommands and flags in `plugin.toml` would make the terminal work,
but it duplicates what `COMMANDS` already says, and the two would drift exactly
as `[[api]]` and the router did in v0.1.0. That is a host change, not a library
change: it needs `[[cli]]` in the manifest, a `PluginCommand` in `anth-panel`
that builds `argv`, and the drift test extended to compare `[[cli]]` against
`COMMANDS`. The plugin's mapper does not change either way, because it reads
`CliRequest` regardless.

Rejected: having the host parse flags and hand the plugin an object of named
values. That reintroduces the original defect — the host deciding the plugin's
vocabulary instead of translating its own transport — and a plugin would then
need two shapes for one action.

## Phases

| Phase | Scope | State |
| --- | --- | --- |
| A | `anth-wire`: length-prefixed framing, unified `WireError`, `HostInfo` | done |
| B | `anth-host`: `/proc` parsing behind a root, no `unsafe` | done |
| C | `anth-panel`: Unix-socket daemon, CLI client, `host-info` end to end | done |
| D | HTTP API over the same dispatch; root `frontend/` on it; example plugin | done |
| E | Port the remaining inspectors feature by feature, each with pagination | pending |
| F | Embed the built frontend in the binary; delete the v0.1.0 tree | pending |

Phase A–C exist so the new layering is proven end to end before any of the
remaining features are ported: a wire format that only has tests is a claim, a
wire format that carries a real request from a CLI through a socket to the
daemon and back is evidence.

## What phases A–C produced

| | v0.1.0 | v0.2.0 so far |
| --- | --- | --- |
| Framing | newline-delimited, 1 MiB line cap | length-prefixed, 64 MiB frame limit |
| Truncation passes | 5 (`process`, `network`, `firewall`, `volumes`, `accounts`) | 0 |
| Error kinds | 6 feature-specific enums | 1 enum, 7 kinds |
| Status and exit-code mapping | derived separately in `api` and the CLI | derived from the kind, once |
| Dispatch | 50 + 43 + 9 match arms across three files | 1 match |
| Tests | 919 Rust | 306 Rust, 96 Bun |
| Transports | socket + HTTP, each with its own dispatch | socket + HTTP over one `dispatch` |
| CI | none | fmt, clippy `-D warnings`, Rust tests, Bun typecheck/tests/build, plugin bundle |

The test count is not a regression: the rewrite has ported one feature. The row
that matters is the first four.

Phases D and the plugin work are verified the same way:
`cargo fmt --check`, `cargo clippy --workspace --all-targets -- -D warnings`,
`cargo test --workspace`, `bun run typecheck`, `bun test` and
`plugins/hello/package.sh` all pass, and the binary serves a real `host-info`
request over a real socket: that is verified by hand as well as by the tests,
because the tests could in principle drive the wrong entry point.

## Deliberately deferred

- **Pagination shape.** No list request exists yet, so no `limit`/`cursor` field
  does either. The concrete shape is decided when the first list feature is
  ported, against a real listing rather than a guess: inventing the field before
  there is a caller to honour it is how a protocol grows a field nobody uses.
- **Socket authentication.** v0.1.0 kept the Unix socket unauthenticated and
  relied on file permissions, with HTTP authentication only. That is unchanged
  for now; a peer-credential check (`SO_PEERCRED`) is a candidate for phase D.
